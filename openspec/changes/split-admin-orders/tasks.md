# Tasks

## 1. Split status and gates

- [x] 1.1 Add `split` to `packages/core/config/orders.php` with label `Split`, an empty `mailers` list, an empty `notifications` list, and `exclude_from_reports` set. Do not add `split` to any invoice status list, AWB status, loyalty earn status, or loyalty cancel status. Verify with a core test that an order saved with status `split` is excluded by `Order::reportable()` and that an order in another status is still included.

- [x] 1.2 Add a core gate query for split. It fails when the status is `split` or `dispatched`, when the status is `payment-received` or the status history includes `payment-received`, when a successful capture exists, when both `meta.billing_series` and `meta.billing_number` are filled, when `meta.awb` is filled, or when `meta.erp_sent_at` is filled. Stock that was already taken does not fail the gate. Do not treat `payment-offline` as sent merely because ERP sending is enabled and the timestamp is empty. The same query reports that warning separately: sending is enabled, `meta.erp_sent_at` is empty, and the status is outside `awaiting-payment`, `failed-erp-sync`, and `invalid-address`. Verify with a core test for each failure on its own, for a `payment-offline` order with an empty timestamp passing, for that warning being reported without becoming a failure, and for an order whose latest stock status decreased stock still passing.

- [x] 1.3 Reject product-line edits when the order status is `split`, through the existing product-line gate query, without changing the paid, ERP, invoice, or AWB gates. Verify with the existing product-line gate test that a `split` order is rejected and that an `awaiting-payment` order is not rejected by this new check.

## 2. Split preview and confirm

- [x] 2.1 Add one core operation that, in a single database transaction, locks the order and rejects the save when the caller may not manage orders (`admin` or `sales:manage-orders`) or the split gate query is not empty. On rejection, leave the order, its lines, and stock unchanged. Verify with a core test for an unauthorized user, a captured order, an order with an AWB, an order with `meta.erp_sent_at`, and a `dispatched` order.

- [x] 2.2 In that operation, accept an assignment of original product-line quantities to two or more targets. Reject a unit left unassigned, a unit assigned twice, a line whose assigned quantities do not sum to its original quantity, fewer than two non-empty targets, and an assignment that does not match the locked order's current lines and quantities. A confirmed split creates one order per non-empty target and no partial set when a later step fails. Verify with a core test that a three-way quantity split stores those quantities, an unassigned unit stores nothing, and a thrown failure after the first new order leaves no new order and leaves the original status unchanged.

- [x] 2.3 Calculate each target on its own new cart. Copy the original customer, channel, currency, and billing and shipping addresses. Copy the assigned purchasable, quantity, and line meta, including personalization. Set the coupon code only on the chosen target. Copy loyalty meta only onto the chosen target. Set `shippingOptionOverride` to the original shipping line's identifier, name, and tax class with the administrator's non-negative price, then recalculate. Do not call `createOrder()`, `setShippingOption()`, or the order-creation pipeline. The preview runs this calculation and rolls the transaction back. Confirm stores the calculated line prices, discount breakdown, shipping breakdown, tax breakdown, subtotal, discount total, shipping total, tax total, total, and fingerprint. Verify with a core test that the preview leaves no cart or order behind, an edited shipping price is the stored shipping total and is included in tax, an unpriceable method starts the preview at zero and still accepts an entered price, and the stored shipping identifier is the original one.

- [x] 2.4 Apply coupon and automatic-discount rules during that calculation. The chosen target is the only order whose discount includes the coupon. When the original order qualified, do not reject the chosen target for being under the coupon minimum spend, and do not clear the coupon code. When that coupon already appeared on the original order, still apply it if the discount has since expired or no longer lists the assigned products. Calculate a percentage coupon from that target's products. Apply a fixed coupon up to that target's product total when the coupon amount is larger. An explicit "do not apply" prices every new order without that coupon. Automatic line discounts and Buy X Get Y are whatever that target's own cart calculation produces. Verify with a core test that a coupon lands on only the chosen order, a target below the coupon minimum still stores the coupon, an expired original coupon still stores, a product-limited original coupon still stores on products outside that limitation, a fixed coupon larger than the target's products is stored up to that product total, "do not apply" stores no coupon, and a line discount stays on the order that received that product.

- [x] 2.5 On confirm, store each new order as placed, with its own reference from `OrderReferenceGenerator`, `new_customer` false, and copied notes, customer, and user. Status is `payment-offline` for `cash-on-delivery`, `cash-in-hand`, and `offline`, and `awaiting-payment` otherwise. Store the selected `payment_option` and `payment_type`. Do not copy transactions, `awb`, invoice identifiers, invoice timestamps, or `erp_sent_at`. Set `meta.split_from_order_id` on each new order and `meta.split_into_order_ids` on the original. Set the original status to `split` with a normal save, not `UpdatesOrderStatus`. Do not dispatch `OrderPlacedEvent` or `MarkAsNewCustomer`. Verify with a core test for both initial statuses, a distinct reference, copied addresses, no copied capture, both meta links, and the original lines still present.

- [x] 2.6 Do not call `decreaseStock()` or `increaseStock()` from the split. Allow the save when stock was already taken. A `preorder` variant included in a successful split keeps its stock and backorder. Verify with a core test that a successful split leaves an `in_stock` variant's stock unchanged, a `preorder` variant's stock and backorder unchanged, and an order whose latest stock activity is `prepare-shipment` still splits with that stock unchanged. The storefront stock actions skip a second decrease for a new order whose source order already took stock, and restore that new order's quantities when it is canceled.

## 3. Loyalty move

- [x] 3.1 After the chosen order has its loyalty meta, and still inside the confirm transaction, dispatch a synchronous event with the original order, the chosen order, and whether the redemption was applied. The loyalty listener moves `order:{original}:spend` onto the chosen order only when that spend exists and the chosen order accepts every point. It uses a unique event key and does not spend the points a second time. When no spend exists, the listener does not write a ledger row. "Do not apply" is rejected when a spend exists and is allowed when it does not. A failed confirm does not dispatch the event. Skip the listener when loyalty is disabled. Verify with a loyalty test that a successful split moves the spend and the balance, a target that cannot accept the full spend leaves the original spend in place, and a rolled-back confirm leaves the balance unchanged.
