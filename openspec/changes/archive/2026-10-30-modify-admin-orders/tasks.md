# Tasks

## 1. ERP send timestamp

- [x] 1.1 In `ErpService::sendOrder()`, when the exporter returns true, set `meta.erp_sent_at` to the current time with `Order::withoutEvents` and save that meta only. Leave the order status unchanged. Do not set the key when the exporter returns false or throws. Verify with `php artisan test tests/ERP/Unit/Listeners/SendOrderToERPTest.php` and `php artisan test tests/ERP/Unit/Filament/Actions/ResendOrderToErpActionTest.php`: a successful send stores a timestamp and keeps the status, and a failed send leaves `meta.erp_sent_at` empty.

## 2. Edit gates

- [x] 2.1 Add a core query that returns the failed gates for an order: `paid`, `erp`, `invoice`, and `awb`. Paid means status `payment-received` or a successful capture, including when a refund exists. An intent with no capture, and no capture at all, are unpaid. Invoice means both `meta.billing_series` and `meta.billing_number` are filled. AWB means `meta.awb` is filled. ERP means `meta.erp_sent_at` is filled, or an enabled provider can send orders and the timestamp is empty and the status is outside `awaiting-payment`, `failed-erp-sync`, and `invalid-address`. An empty timestamp with no enabled send provider is not an ERP failure. Verify with a core test that covers each gate on its own, a refunded capture still failing `paid`, one invoice identifier not failing `invoice`, and an `awaiting-payment` order with an empty timestamp not failing `erp`.

## 3. Product-line save

- [x] 3.1 Add one core operation that, in a single database transaction, locks the order, rejects the save when the gate query is not empty or the authenticated user cannot manage orders (`admin` or `sales:manage-orders`), and rejects the save when `cart_id` is missing. On rejection, leave order lines, totals, and the cart unchanged. Verify with a core test for a captured order, an order with an AWB, an order with both invoice identifiers, an order with `meta.erp_sent_at`, a `payment-offline` order with no timestamp while sending is enabled, a user without `sales:manage-orders`, and an order with no cart.
- [x] 3.2 In that same operation, align the linked cart with the order (customer, channel, currency, coupon from the discount breakdown, loyalty meta, and the shipping option identifier), rebuild the cart product lines from the order lines including line meta, then apply one change: set a line quantity, add a purchasable variant, or remove a line. Adding a variant that matches an existing line's purchasable and meta increases that quantity. Reject a quantity below 1, a quantity the variant's minimum or increment rules reject, a variant that is not purchasable, and removal of the last product line. Do not call `createOrder()` or the order-creation pipeline. Verify with a core test that a rejected quantity and a last-line removal leave the stored order unchanged, and that adding an existing variant does not create a second line.
- [x] 3.3 Treat stock as taken only when the latest `status-update` from `Order::getActivitiesByStatuses()` over `lunar-frontend.orders.stock.decrease` and `.increase` has a decrease status. When stock is not taken, leave variant stock unchanged and do not reject the save with `CartLineStock`. When stock is taken, `increaseStock()` by a removed quantity or by a quantity cut, and `decreaseStock()` by an added quantity after `CartLineStock` accepts only that added quantity. Do this inside the order transaction so a failed save restores the stock. Verify with a core test: a `prepare-shipment` activity returns stock when a line is removed and when a quantity drops, takes stock when a quantity rises and the extra units exist, rejects the rise when they do not, and an order with no stock activity or with a later `canceled` activity leaves stock unchanged.
- [x] 3.4 Recalculate the cart and copy product lines, the shipping line, and order totals back onto the order: unit price, subtotal, discount total, discount breakdown, shipping total, shipping breakdown, tax total, tax breakdown, total, and fingerprint. Keep status, reference, `placed_at`, customer, addresses, notes, payment meta, and the shipping option identifier. Keep personalization meta on a line whose quantity changes. If the current shipping option cannot be priced, roll the transaction back. Verify with a core test that a quantity change updates the stored line quantity and order total from the cart calculation, keeps status and reference, keeps personalization meta, and that an unpriceable shipping option leaves the order unchanged.
- [x] 3.5 After the order meta has the recalculated `loyalty_points_to_redeem`, dispatch a synchronous event inside the transaction. In the loyalty package, listen for it and, when `order:{id}:spend` exists and the point count changed, adjust the ledger by the signed difference with a unique event key. Return points with a positive adjust tied to that spend. Spend more with a negative adjust. Do not call `spendForOrder()` again. Skip the ledger when no spend row exists or loyalty is disabled. Verify with `php artisan test` on a new loyalty test: fewer redeemed points increase the balance and update the order meta, and a rolled-back save leaves the balance unchanged.
