# Proposal

## Why

Shops receive product lists from suppliers as Excel or CSV files, and every supplier uses different column names, languages, and column orders. Shops that move from another shop platform bring that platform's product export, with its own row structure and value formats. Today the only way to get those products into the catalog is to type them in one by one or to build a one-off ERP integration. Staff need an import that understands an arbitrary spreadsheet or another shop's export, lets them check and correct everything first, and only then writes to the catalog (LFP-954).

## What Changes

- A new monorepo package, `packages/product-import` (`Lunar\ProductImport`), adds an AI-assisted product import to the Lunar admin as a Filament plugin. A config flag turns it on, and a new staff permission, `catalog:import-products`, controls access. Staff start it from an **Import** button on the product list. Past imports are listed under Catalog.
- Staff upload one or more XLSX, XLS, or CSV files into one import, so a products file and its separate variants file are imported together. For CSV files they can choose the character encoding in the upload form, so files with different encodings can be imported one after another. Every sheet is read into the package's own staging tables, and the reader records which cells the spreadsheet itself stores as numbers or dates. For each column the system computes the fill rate, the uniqueness, and up to 30 sample values. It does not guess what a column holds: the AI reads that from the samples, and the target that staff confirm decides how the column is read. The Lunar catalog is not touched until staff approve the import.
- For each sheet, one AI request suggests which webshop field each column holds and how rows group into products and variants. Each suggestion comes with a confidence value. For every column that holds numbers or dates, the AI also gives the column's format: its decimal and thousands separators, or its date format. For every column of lists, it gives the separator between items, for a category column also the separator between levels, and for packed items the separator between their parts. For a sheet with weight or dimension columns, it gives the weight and length unit, chosen from the store's units. For columns written in an export's own conventions, it gives the meaning of each code, the parts of packed list items, and the size suffix of thumbnail URLs. The program does not guess separators, units, or codes, and has no default for them. The request carries only the headers, the column statistics, and a limited number of sample values per column, never the whole file. The AI has no tools and no database access. Its answer must match a JSON schema that we define, its target fields come from a fixed list, and the system checks the answer before using it. The provider, model, and optionally a separate API key come from the environment, so each shop can use any `laravel/ai` provider. When the AI fails, staff see a clear message and can retry. There is no automatic fallback.
- Exports of other shop platforms are read through the conventions they use, without any platform-specific code, configuration, or choice. These conventions are:
  - a row type column that marks single products, products with variant rows, variants, and rows not to import;
  - parent references by ID or SKU, also into a separate variants file;
  - option name and value column pairs that variant rows number differently;
  - packed `Name:Value` items with extra parts such as types and positions;
  - coded status, stock, backorder, and shippable values;
  - price and weight impacts, and prices with and without tax;
  - formula escapes, literal line breaks, and HTML entities in cells;
  - thumbnail URLs with a size suffix;
  - headers in any language and order.

  Products with their variants, options named in cells, plain attributes and features, tags, GTIN and MPN, dimensions, stock status and backorders, sale prices with their dates, up-sells and cross-sells, SEO fields and URL slugs, and images are imported. Any export that uses these conventions is read the same way, whichever platform wrote it.
- SEO fields and URL slugs are imported when a file has them. Meta titles, descriptions, and keywords go into the product type's text attributes that hold them, such as the `product-meta-title`, `product-meta-description`, and `product-meta-keywords` attributes that the `lunar-frontend` seeder creates. The code names no SEO handle: the AI maps these columns like any other attribute. A slug column gives a new product its URL in that language, so a shop that moves keeps its addresses. Without a slug column, Lunar generates the URL from the product name, as before. Existing products keep their URLs.
- Staff review and change the mapping for each sheet. They can ignore columns, map columns by hand, correct the code meanings, item parts, and image size suffixes of columns, choose how rows group into products, set the weight and length units of a sheet, and correct the number and date format and the list, path, and item separators of every column. A product can be in several categories, split on its category column's separators. Staff also set the import options: the status of new products (draft, published, or from a status column) and collections that every imported product is also added to. Changing the mapping never calls the AI again.
- A separate review step collects every distinct category, brand, option name, option value, and product property from all sheets. It shows which ones already exist, which are similar to an existing one, and which are new, and how many products use each. Staff decide whether to use an existing record, create a new one, merge several values into one, or skip the value. A property is written into a product attribute that staff choose, or skipped.
- Code validates every row: required fields, data types and the column formats, duplicate SKUs, parent references, and conflicts inside a product group. A preview shows the products and variants that will be created or updated, with every warning and error. Staff can correct or skip single rows before importing. Nothing reaches the catalog while an error is unresolved, except rows staff explicitly skip.
- On approval, queued jobs first create the approved brands, categories, options, and option values, then create or update products, variants, and prices in transactional groups, then add up-sells and cross-sells, and finally download the images. Existing variants are matched by SKU or EAN, so running the import again does not create duplicates. Only mapped fields are overwritten.
- Import history keeps each import's status, statistics, and mapping. Failed rows can be downloaded as CSV, corrected, and retried. Images that failed to download are listed with their reason, and staff can correct their URLs and retry them. Staging rows and the uploaded files are pruned after a configurable retention period.
- Approved mappings can be saved as named profiles. When a later file has matching headers, the system offers the profile, and applying it skips the AI call.
- Actions that lose a race against another request are refused with a general message, because the system cannot know what changed the import in the meantime. The message that an import is being processed is shown only when its stored status says so.
- The package handles strings through Laravel's `Str` helpers instead of PHP's native string functions, so non-breaking and zero-width spaces from spreadsheets are trimmed like ordinary spaces.
- New dependency: `maatwebsite/excel` ^4.0, which brings in `phpoffice/phpspreadsheet`. `laravel/ai` ^1.4, already installed through `minic/laravel-ai-assistant`, becomes a direct requirement.

## Capabilities

### New Capabilities

- `catalog/product-import`: Access, entry points, the import lifecycle and its statuses, cancelling, import history, and staging retention.
- `catalog/product-import-file-reading`: Supported file formats and limits, several files per import, sheets, header detection, CSV delimiter detection and the CSV encoding chosen at upload, cells stored as numbers or dates, and the column profile computed per sheet.
- `catalog/product-import-ai-analysis`: The AI column-mapping suggestion: what is sent, the answer format with column formats, separators, units, and conventions, its checks, confidence, provider configuration, failures, and retry.
- `catalog/product-import-column-mapping`: The target fields, mapping and ignoring columns for each sheet, the number and date format and the list, path, and item separators of each column, SEO columns and URL slugs, product and variant grouping, including grouping by parent reference, option names and values in cells, several categories per product, the weight and length units per sheet, import options and defaults (the status of new products and additional collections), and re-staging after a mapping change.
- `catalog/product-import-export-conventions`: The export conventions the import reads without knowing any platform: row types, parent references across rows and files, option pairs and packed list items, coded values, cell escapes, image size suffixes, prices with and without tax, translated headers, SEO columns and URL slugs, and the columns that have no catalog counterpart.
- `catalog/product-import-profiles`: Saving approved mappings as import profiles, recognizing matching files, and applying a profile instead of calling the AI.
- `catalog/product-import-taxonomy-review`: Collecting categories, brands, option names, option values, and properties, matching them to existing records, and staff decisions to use an existing record, create, merge, or skip.
- `catalog/product-import-validation`: Normalizing values with the column formats and separators, validation rules, values that cannot be read, the preview of products and variants, and correcting or skipping single rows.
- `catalog/product-import-commit`: Writing approved data to the catalog: order of operations, matching and updating without duplicates, transactions, sale prices, tags, URL slugs, associations, images, side effects, results, error report, and retrying failed rows and failed images.

### Modified Capabilities

None. No existing catalog behavior changes, and the admin product create flow is untouched.

## Impact

- New package `packages/product-import`: service provider, Filament plugin, config, migrations for seven tables (`lunar_product_imports`, `lunar_product_import_files`, `lunar_product_import_sheets`, `lunar_product_import_rows`, `lunar_product_import_values`, `lunar_product_import_images`, and `lunar_product_import_profiles`), en, hu, and ro translations, permission state, and a scheduled prune command.
- Root `composer.json`: autoload, autoload-dev, provider, `extra.lunar.name`, and `replace` entries for the new package. New `require` entries `maatwebsite/excel` and `laravel/ai`. `phpunit.xml` gets a `product-import` test suite, and the tests go under `tests/product-import`.
- Admin: an **Import** header action on `ListProducts` through a `ListPageExtension`, a new `ProductImportResource` under the Catalog navigation group, and a new permission label in **Access Control**.
- Catalog writes through `Product`, `ProductVariant`, `Price`, `Brand`, `Collection`, `ProductOption`, `ProductOptionValue`, `ProductAssociation`, tags, and the media library. Their existing events still fire. Scout indexing is deferred and run once per import. Klaviyo product sync jobs are unique per product and dispatched after commit, so they collapse per product. Mailchimp and the ERP have no product observers.
- Outgoing HTTP: images are downloaded from the URLs in the file, only over HTTP and HTTPS, never from private or local network addresses, and within configured size and time limits.
- Queue: the jobs run on the application's default queue connection and queue. `PRODUCT_IMPORT_QUEUE` and `PRODUCT_IMPORT_QUEUE_CONNECTION` can move them to another queue or connection, for example a `product-import` queue.
- Environment: `PRODUCT_IMPORT_ENABLED`, `PRODUCT_IMPORT_AI_PROVIDER`, `PRODUCT_IMPORT_AI_MODEL`, `PRODUCT_IMPORT_AI_API_KEY`, `PRODUCT_IMPORT_AI_URL`, `PRODUCT_IMPORT_RETENTION_DAYS`, and the queue settings.
- Host app (`lunar-frontend`, separate repository): registering `ProductImportPlugin` when `lunar.product-import.enabled` is true, as is already done for the other plugins. This is a follow-up outside this change.
- Docs: `docs/system/CODE_MAP.md`, `docs/database/schema.dbml`, and the daily changelog file.
- Out of scope: AI normalization of values (for example "rosu" to "Piros"); deleting or deactivating catalog records that a file does not contain (an import is not a sync); export conventions that no supported export uses yet, such as continuation rows, which are added later as general rules; tax classes, shipping classes, downloadable files, and other export fields without a catalog counterpart, which are listed as not imported; SEO fields of categories, because a product file names a category only by its path.
